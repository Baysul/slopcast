# Task 8: Migrate Hand-Rolled `components/ui/` to Genuine shadcn/ui

**Date:** 2026-07-29
**Task ref:** AGENTS.md §8, Task 8
**Status:** Research complete — ready for implementation planning

---

## 1. Feature Summary & Stated Assumptions

### What Task 8 asks for

> Migrate the hand-rolled `components/ui/*` in both frontends to genuine shadcn/ui (cva
> variants, Radix primitives, CSS-variable tokens) via `shadcn-ui-mcp`.

### Restated scope

Replace every hand-rolled UI primitive in both the **Desktop** (`apps/desktop`) and **Web**
(`apps/web`) apps with shadcn/ui components generated by the CLI. The deliverables are:

- CSS custom properties (OKLCH or HSL-based design tokens) replacing hardcoded hex values
- `class-variance-authority` (CVA) variant definitions instead of manual `clsx` variant objects
- Radix UI (or Base UI) primitives for accessibility and behaviour
- All existing call sites updated to use the new component APIs

### Assumptions

1. Both frontends are migrated together using the same shadcn components, colour token map, and CSS variable definitions — they share identical palettes, `Badge`, `cn()`, and `index.css` today, and that symmetry should be preserved.
2. Domain-specific components that have no shadcn equivalent (`AudioLevelMeter`, `AudioVisualizer`, `SpectatorTelemetryBar`, `StreamTelemetryBar`, `Sparkline`) are **not** in scope; they stay as-is and may be relocated out of `components/ui/` where appropriate.
3. The extracted-but-dead components under `apps/desktop/src/renderer/components/` (Header, ScreensharePreview, AudioPickerPanel, SourcePickerPanel, StreamSettingsPanel) and `usePresenter.ts` hook are **Task 9** territory — they reference a mismatched IPC API surface and cannot be activated without additional reconcilation. This report notes them as follow-up work but does not propose migrating them here.
4. The project stays on the **Radix UI** primitives base (`shadcn init -b radix`) — Radix is mature, well-understood, and already proven in the broader ecosystem. Base UI is the new shadcn default (July 2026) but introduces unfamiliar API surface with no benefit for this project.
5. The `shadcn-ui-mcp` MCP server is available for component scaffolding and resolving the shadcn registries; it should be used as the primary tool for adding components rather than manual `npx shadcn@latest add` shellouts.

## 3. The Prerequisite Decision: Tailwind v4

The shadcn CLI generates Tailwind v4-flavoured components (OKLCH colour space, `tw-animate-css` animations, CSS-based `@theme` configuration). Adopting them requires upgrading Tailwind from v3.4.17 → v4.

### Option A: Full Tailwind v4 upgrade (recommended)

**Upside:**
- Can use `npx shadcn@latest add` to pull components from the registry — zero manual copy-paste
- Ongoing CLI compatibility for future components (Dialog, Select, Tooltip, etc.)
- OKLCH colour space is perceptually uniform and the new standard
- Tailwind v4 is faster, CSS-first, and removes `tailwind.config.js` boilerplate
- Single source of truth for theming via CSS custom properties

**Downside:**
- Touches every Tailwind config and build tool in both apps
- Requires migrating `tailwind-merge` v2 → v3
- Requires replacing `postcss`/`autoprefixer` with `@tailwindcss/vite` in Vite config
- Risks: undocumented Tailwind v4 class name changes, potential breakage in the monolithic `main.tsx`
- ~1–2 days of focused migration work before any shadcn component can be added

### Option B: Stay on Tailwind v3, manually copy shadcn component source

**Upside:**
- Zero Tailwind migration risk
- Can add `@radix-ui/react-slot`, `@radix-ui/react-toast`, and `class-variance-authority` without touching the build pipeline
- Components are ~40–100 lines each; manageable to copy

**Downside:**
- Locked out of `shadcn add` — all future components must be copied manually
- Component updates (upstream fixes, new features) require manual diffing
- The project already has `components.json` pointed at the v4 registry — component source from the registry would use v4 patterns (OKLCH vars, `@theme`, `tw-animate-css`) that don't work in v3
- Different code style between hand-copied shadcn components and everything else

### Option C: Tailwind v4 upgrade on web first, desktop later

Staggers the risk but forces two separate theming migration efforts. Not recommended — the colour palettes are identical and should stay in lockstep.

### Recommendation: Option A

The project already has 80% of the setup done (`components.json`, `cn()`, `lucide-react`, icon library). Blocking on Tailwind v3 just delays the inevitable — every new shadcn component added later would face the same version mismatch. The Tailwind v4 migration is mechanical and well-documented; once done, all shadcn work can proceed via CLI.

## 4. Component Migration: Mapping & Tradeoffs

### 4.1 Components to replace

| Current hand-rolled | Target shadcn | Complexity | Call sites | Notes |
|---|---|---|---|---|
| `Badge` (both apps) | `shadcn Badge` | Low | Desktop: 1 (Header in main.tsx). Web: 2 (RoomPage, Header) | Need to extend CVA variants to include `live`/`info`/`disconnected` with safelight colour mapping |
| `Button` (web) + inline buttons (desktop) | `shadcn Button` | Medium | Web: 3 files, ~8 instances. Desktop: ~12 `<button>` elements inline in main.tsx | shadcn Button uses `@radix-ui/react-slot` for `asChild` polymorphism. Desktop buttons currently use raw `<button>` tags with Tailwind classes |
| `Input` (web) | `shadcn Input` | Low | Web: 1 (HomePage, room code field) | shadcn Input is a thin `forwardRef`-wrapped `<input>`. The error-message pattern should use shadcn Form patterns (or stay as a simple prop) |
| `Card` (web) + inline cards (desktop) | `shadcn Card` | Medium | Web: 1 (HomePage). Desktop: ~5 `<div>` panels in main.tsx | shadcn Card is compound (`Card`, `CardHeader`, `CardTitle`, `CardDescription`, `CardContent`, `CardFooter`). The desktop panels currently use flat `<div>`s |
| `Toast` (desktop) | `shadcn Toast` | **High** | Desktop: 1 viewport + ~12 `addToast()` call sites in main.tsx | Custom `useToasts` hook → imperative `toast.add()` API. Audio chime synthesis must be ported. The toast types (`success`, `info`, `error`) map to `type: "success"`/`"info"`/`"error"` |
| `AudioLevelMeter` (desktop) | N/A | None | Remove from `components/ui/`, relocate to e.g. `components/audio/AudioLevelMeter.tsx` | Not a general UI component — domain-specific canvas visualization |

### 4.2 New shadcn components to add (opportunistic)

These replace inline Tailwind patterns in `main.tsx` and improve consistency:

| Component | Where used | Priority |
|---|---|---|
| Select | StreamSettings (codec, resolution, fps dropdowns) | Medium |
| Tooltip | Copy button, refresh button, info icons | Low |
| Dialog | Settings modal (if StreamSettings moves to a modal) | Low |

### 4.3 Toast migration tradeoffs

The desktop `Toast.tsx` (216 lines) is the single most complex migration item:

| Aspect | Current (hand-rolled) | shadcn (@radix-ui/react-toast) | Impact |
|---|---|---|---|
| State management | `useState<Toast[]>` in `useToasts` hook | Imperative `toast.add()` with internal Radix provider | Every `addToast()` call site changes signature |
| Audio chime | Web Audio API `OscillatorNode` synth on every toast | Must be re-implemented as a callback or side-effect wrapper | ~30 lines to port |
| Dismiss behaviour | Manual `setTimeout` + click-to-dismiss | Radix handles swipe, auto-dismiss via `duration` prop | Simplifies: remove `setTimeout` logic |
| Variants | `success` / `info` / `error` | `default` / `destructive` (plus custom `type`) | `addToast({ variant: 'error' })` → `toast.add({ type: 'error' })` |
| Accessibility | Manual `role="alert"` / `role="status"` | Radix handles ARIA announcements natively | Improvement |
| Viewport | Fixed bottom-right, 3-toast stack | Radix `ToastViewport` with configurable position | Layout identical |

**Recommendation:** Replace the toast system as a single focused PR after all simpler components (Badge, Button, Input, Card) are migrated. The imperative API is a known pattern; the chime synthesis can be extracted into a small `useNotificationSound()` hook.

## 5. Recommended Approach

### 5.1 Execution order (sequential within each phase; phases can be parallelized where noted)

#### Phase 1: Tailwind v4 upgrade (both apps — can run in parallel)

1. **Convert Tailwind config to CSS.** Move all colour tokens from `tailwind.config.js` to CSS custom properties in `index.css`:
   ```
   :root { --background: 222 47% 7%; --foreground: 210 20% 98%; ... }
   ```
   Convert hex → OKLCH via [shadcn/create](https://ui.shadcn.com/create) theme builder or manual tools. Both apps share the same palette so process once, copy to both.

2. **Switch to `@tailwindcss/vite`.** Replace PostCSS plugin with the Vite plugin in `vite.config.ts` for both apps.

3. **Update `tailwind-merge`** to v3.x in both `package.json` files.

4. **Add `tw-animate-css`** (replace `tailwindcss-animate`). Import in `index.css`.

5. **Remove `tailwind.config.js`** files (no longer needed in v4).

6. **Verify.** Build both apps, run the E2E test (`pnpm test:e2e`), visually smoke-test the desktop and web apps. Every colour, layout, and animation must match pre-migration behaviour.

#### Phase 2: Foundation shadcn packages (both apps)

7. **Install shared dependencies:** `class-variance-authority`, `@radix-ui/react-slot`, `@radix-ui/react-toast` (and any others required by the components being added).

8. **Verify `components.json`** is still valid post-Tailwind-v4. Update `tailwind.config` field to empty (v4 convention).

#### Phase 3: Component replacement (web app first — smaller surface, lower risk)

9. **Replace Badge** (both apps — identical code, do once and copy). Extend CVA variants:
   ```
   variants: {
     variant: {
       default: 'bg-primary text-primary-foreground',
       secondary: 'bg-secondary text-secondary-foreground',
       destructive: 'bg-destructive text-destructive-foreground',
       outline: 'text-foreground',
       // App-specific:
       live: 'bg-safelight/20 text-safelight border-safelight/30',
       disconnected: 'bg-muted text-muted-foreground',
       info: 'bg-accent text-accent-foreground',
     },
   },
   ```

10. **Replace Button** (web). Map existing variant names: `primary` → `default`, `outline` / `ghost` / `destructive` → same names, `secondary` → `secondary`. Size names match exactly.

11. **Replace Input** (web). The error-message `<p role="alert">` pattern stays as-is (shadcn Input is just the `<input>`, not a FormItem wrapper).

12. **Replace Card** (web). Switch from single `<Card>` wrapper to compound `<Card>`/`<CardHeader>`/`<CardTitle>`/`<CardContent>` decomposition in HomePage.

13. **Replace desktop inline buttons/cards/inputs.** This is the labour-intensive step: `main.tsx` has ~12 buttons, ~5 card panels, and a few inputs all defined inline. Each must become a shadcn component import. This is also where **Task 9** (decomposition) naturally overlaps — extracting panels like StreamSettingsPanel and AudioPickerPanel should happen concurrently.

#### Phase 4: Toast migration (desktop)

14. **Replace the toast system.** Remove `useToasts` hook and `ToastViewport`. Replace with shadcn Toast (`@radix-ui/react-toast`). Port audio chime to a standalone `useNotificationSound()` hook. Update all `addToast()` call sites.

#### Phase 5: Cleanup

15. **Relocate `AudioLevelMeter`** from `components/ui/` to a domain folder (e.g., `components/audio/`).

16. **Remove dead extracted components.** `Header.tsx`, `ScreensharePreview.tsx`, `AudioPickerPanel.tsx`, `SourcePickerPanel.tsx`, `StreamSettingsPanel.tsx`, and `usePresenter.ts` — they reference an IPC API surface that doesn't exist and have been superseded by the inline code in `main.tsx`. Remove them to avoid confusion.

17. **Run E2E test** to validate the full presenter → spectator flow still works.

### 5.2 Estimated effort

| Phase | Effort | Risk |
|---|---|---|
| Tailwind v4 upgrade | 1–2 days | Medium — colour regressions possible |
| Foundation packages | 1 hour | Low |
| Badge replacement | 1 hour | Low |
| Button replacement (web) | 1 hour | Low |
| Input replacement (web) | 30 min | Low |
| Card replacement (web) | 30 min | Low |
| Desktop inline → shadcn | 2–3 days | Medium — main.tsx is monolithic |
| Toast migration | 1 day | Medium — API change at every call site |
| Cleanup | 1 hour | Low |
| **Total** | **5–8 days** | |

The Tailwind v4 upgrade and the desktop main.tsx decomposition dominate the timeline. Component replacement itself is fast once theming is in place.

## 6. Open Risks & Unresolved Questions

1. **Tailwind v4 class name breakage.** Tailwind v4 renames several utility classes (e.g., `grow`/`shrink` replacing `flex-grow`/`flex-shrink`, `rounded-l` → `rounded-s`, etc.). The monolithic `main.tsx` has ~1500 lines of Tailwind classes; an automated migration may miss some. **Mitigation:** Run the official Tailwind upgrade tool, then visually diff the apps before and after.

2. **`main.tsx` decomposition overlap with Task 9.** Replacing inline buttons/cards/panels with shadcn components in `main.tsx` is naturally also decomposition work. The boundary between Task 8 and Task 9 will blur. **Recommendation:** Treat them as a combined effort — as each panel is extracted into a component, give it shadcn primitives from the start.

3. **Toast API churn.** The shadcn toast API has changed three times in 18 months (Radix `useToast` → sonner `toast()` → Base UI `toast.add()`). The Radix toast used here is stable but may diverge from upstream conventions. **Mitigation:** Pin `@radix-ui/react-toast` version and audit on dependency bumps.

4. **Dead extracted components — keep or delete?** The five extracted components and `usePresenter.ts` use a different `electronAPI` surface than the working code. They are bit-rot. **Recommendation:** Delete them. They'll be rebuilt properly during Task 9 decomposition from the working `main.tsx` code, not from these stubs.

5. **Shared UI package opportunity.** ~120 lines are duplicated between desktop and web (Badge, cn(), CSS, Tailwind theme). After this migration, that number will grow (both apps will have identical shadcn component files and CSS variables). **Recommendation:** Defer to a follow-up task — create `packages/shared-ui` as a workspace package that both apps import. Not in scope here.

6. **CSS variable naming collision.** The project uses `safelight` as a brand colour name. shadcn expects standard tokens (`primary`, `secondary`, `accent`, etc.). `safelight` should map to `--primary` in the new theme, with the existing accent/gray tokens filling the other slots. This is a design decision — the colour mapping table must be agreed before Phase 1 begins.
